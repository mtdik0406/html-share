# 11. レビューのエージェントの数と、手元の変異テストの範囲を、差分の大きさで決める

- 日付：2026-11-21
- 状態：採用

## 状況

[ADR 8](0008-single-develop-skill.md) の develop の skill は、差分の大小に関係なく 4 つの観点ごとにエージェントを立て、直したあとももう一度立てていた。どのエージェントも AGENTS.md・README・ADR のすべてとコードを読むので、同じ文書を何度も読ませることになり、トークンを多く使っていた。

変異テストは、手元でも毎回全体（変異 1,600 個ほど、約 2 分）を流していた。

## 決定

- `pnpm run review:scope` が、main からのコードの差分の行数と、レビューのエージェントの数を出す。300 行未満は 1 体、1000 行未満は 2 体、それ以上は 4 体
- エージェントには、差分の範囲と、関係する ADR の番号を渡す。ADR をすべて読ませない
- 直したあとにもう一度見るのは、高か中の指摘を直したときだけにし、1 体にする
- 手元の変異テストは `pnpm run test:mutation:scope` で、変えたファイルと、変えたテストと同じ名前のソースだけを流す。Stryker の incremental で前回の結果を再利用する
- CI は incremental の結果を持たないので、毎回全体を流す

## 理由

- 差分が小さいときは、観点を分けても見つかる指摘がほとんど増えない
- incremental は、変異の対象のファイルとテストのファイルの変更を見て、変わったものだけを流し直す（StrykerJS の incremental のドキュメント）。手元の 2 回目からは数秒で終わる

## 捨てた案

- incremental を使わず、変えたファイルだけを毎回流す：差分の大きいブランチでは 1 分ほどかかる
- 手元では変異テストを流さず、CI に任せる：見逃した変異を、push するまで知ることができない

## 結果

- incremental は、依存の更新や、変異の対象でもテストでもないファイル（設定など）の変更を見ない。tap のテストは、ファイルの中の 1 つを変えるとファイル全体が変わったとみなされる。手元の結果が怪しいときは `pnpm exec stryker run --force` で流し直す。CI の全体の実行が最後の歯止めになる
- 差分の行数でエージェントの数を決めるので、行数の少ない重い変更（権限やヘッダーの 1 行など）は 1 体で見る
