# 11. 秘密鍵の SSM のパラメータを、鍵の世代ごとに分ける

- 日付：2026-11-21
- 状態：採用

## 状況

[ADR 10](0010-signing-key-generation.md) では、鍵を作り直すときに 1 つのパラメータを新しい秘密鍵で上書きしてから deploy する。deploy が失敗すると、SSM は新しい鍵、CloudFront は古い公開鍵のままになる。古い秘密鍵に戻すには手元の秘密鍵が要るが、[ADR 9](0009-sign-in-lambda-with-ssm-key.md) で手元の秘密鍵は消している。

## 決定

- パラメータの名前を世代から決める。1 世代目は `/html-share/signing-private-key`（今の名前のまま）、2 世代目からは `/html-share/signing-private-key-gen<世代>`
- 署名の Lambda が読むパラメータと、ロールに許すパラメータは、スタックの世代のものだけにする
- 鍵を作り直すときは、新しい世代の名前に置き（上書きしない）、deploy で公開鍵・Key-Pair-Id・読むパラメータを同時に切り替える
- 古い世代の鍵は、新しい鍵で署名できると確かめてから `pnpm run keys:delete` で消す。片付けでは `--all` ですべて消す
- ADR 9 の「パラメータは 1 つ」と、ADR 10 の作り直しの順と戻し方は、この ADR で置き換える

## 理由

- deploy が失敗して戻っても、古い世代の公開鍵とパラメータがそのまま使われるので、SSM を戻す作業がいらない。手元の古い秘密鍵も要らない
- 読むパラメータが Lambda の環境変数で変わるので、古い鍵を持った実行環境も deploy で入れ替わる。store と deploy の間に、通らない URL ができない

## 捨てた案

- 1 つのパラメータを上書きし、失敗したら SSM の履歴から古い版を読んで戻す：秘密鍵が手元のメモリに入る
- 1 世代目も新しい名前に移す：今置いた鍵を置き直すために、手元の秘密鍵が要る

## 結果

- 作り直したあと、古い世代の鍵は `keys:delete` で消すまで SSM に残る。Lambda のロールは読めないが、アカウントの IAM プリンシパルは読める
- `keys:delete` は、今の世代より後の世代の鍵（作り直しの途中で置いたもの）を消さない
