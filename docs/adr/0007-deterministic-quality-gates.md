# 7. 品質は、機械で決められることを検査で守り、残りを AI のレビューで見る

- 日付：2026-11-21
- 状態：0008 で置き換え

## 状況

コードの多くを AI が書く。AI の出力は同じ指示でも毎回変わり、文章の規則は守られないことがある。利用者は、できあがったものを確認するだけにしたい。

## 決定

- 機械で決められることは、`pnpm run check` の検査にする：型・書式・lint・関数の複雑さ・リポジトリの約束（`tools/check-repo.ts`）・未使用のコード（knip）・重複（jscpd）・テストと網羅率
- テストの見逃しは、変異テスト（Stryker）で測る。CI で毎回実行し、スコアが `stryker.config.json` の `break` を下回ると落とす。テストで見ないと決めたエラーと警告の文言は数えない
- 変えると利用者の判断が要るファイル（検査の設定と検査そのもの・作業の規則・ADR）は、`tools/lib/review-scope.ts` の 1 か所に並べ、`pnpm run review:scope` で報告に載せる
- 機能を作り終えたら、AI が `quality-review` の skill で、レビュー・確かめ・修正・再確認までを済ませてから報告する。範囲と見逃した変異は、コマンドの出力に従う

## 理由

- 検査は、AI が規則を読み落としても毎回同じ結果を出す
- AI のレビューは、意味の読み取り（攻撃に使えるか、境界値が足りているか）にだけ使えば、ばらつきの影響が小さい

## 結果

- 変異テストの下限は、上げることはあっても下げない。下げるときは新しい ADR で理由を書く
- 検査を足すたびに、わざと違反を入れて落ちることを確かめる
