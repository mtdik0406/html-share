# 18. 変異テストは、テストの見落としを探す手がかりにし、コミットごとのゲートにしない

- 日付：2026-11-23
- 状態：採用
- 置き換えたもの：[ADR 8](0008-single-develop-skill.md) の「テストの見逃しは `review:mutants` の終了コードで決める」、[ADR 11](0011-review-and-mutation-scope.md) のエージェントの数

## 状況

develop の skill は、変えた行に見逃した変異が 1 つもないこと（`review:mutants` の終了コードが 0）を、作業を終える条件にしていた。振る舞いを変えないリファクタリングでは、変える前に、変えるファイルの見逃しを 0 にすることも求めていた。

その結果、次のことが起きた。

- どう変えても振る舞いが同じになる変異にも、テストか `// Stryker disable` のコメントが要った。コードにコメントが 66 か所たまり、その理由の正しさが、レビューの指摘の対象にもなった
- 変異を避けるために、コードの書き方を変えた（正規表現を `endsWith` に、`?? ""` を型の指定に）
- ファイルを移すだけの変更でも、以前からある見逃しを先に片づける必要があった
- 変異の 4 分の 1 は、利用者に届かない `tools/` のものだった
- 差分が 1000 行以上のときの 4 体のレビューは、同じ指摘を重ねて返した。レビューが「この書き方もすり抜ける」と、今のコードにない書き方を挙げ、直すたびに範囲が広がった

## 決定

- 手元の変異テストは、作業の最後に 1 回だけ流す（`pnpm run test:mutation:scope` のあとの `pnpm run review:mutants`）。コミットごとには流さない
- 見逃した変異のうち、直すのは、その変異で結果が変わる入力と、外から見える違いを挙げられるものだけにする。それにはテストを足す。挙げられない変異（結果が同じになるもの、表示の文言）は、テストもコメントも足さずに報告に数だけ載せる。今ある `// Stryker disable` は残す
- 変異テストのゲートは、CI の全体の実行のスコアの下限（`stryker.config.json` の `break`）だけにする。下限は変えない
- 変異の対象（`mutate`）から `tools/` を外す。`tools/` の変更は、単体テストと `lint:repo` などの検査で見る。手元の範囲（`test:mutation:scope`）は、対象の外のソースに対応するテスト（`test/tools/...`）を変えても、全体を流さない
- 振る舞いを変えないリファクタリングでは、変える前の見逃しを 0 にしない。変える前と後で、テストの件数と結果、生成物（`cdk synth` のテンプレートなど）が同じことを確かめる
- レビューのエージェントは 2 体までにする（300 行未満は 1 体、それ以上は 2 体）
- レビューの指摘は、今のコードで起きるものだけを直す。今のコードにない書き方や入力で起きるものは、直さずに報告に載せる

## 理由

- 変異テストが役に立つのは、確かめていない振る舞いを見つけたときだけ。結果が同じになる変異を 0 にしても、テストは強くならない
- 直すかどうかを「結果が変わる入力を挙げられるか」で決めれば、AI の判断のばらつきを、挙げた入力をテストにして確かめられる
- CI の下限があれば、テストが全体として弱くなったことには気づける
- `tools/` は検査そのもので、壊れると検査が落ちるか、レビューで気づく。利用者のデータに届かない

## 捨てた案

- いまのゲートを残し、コメントの書き方だけを軽くする：コードの形を変える圧力と、レビューの手間が残る
- 手元では変異テストを流さない：CI まで見逃しに気づけない（ADR 11 の理由と同じ）
- `infra/` も対象から外す：バケットの公開や権限など、守りの性質を確かめるテストの強さを測れなくなる

## 結果

- `tools/` を外すと、全体のスコアは下がる（`tools/` には見逃しがなかった）。下限は 79 のまま
- 見逃しのうち「挙げられない」と判断したものは、コメントが残らないので、次の作業でも一覧に出る。報告には数だけ載せる
- `tools/lib/` の `// Stryker disable` のコメントは、対象から外すと意味がなくなるので消す
