# 15. core/ には、どの実行環境でも同じでなければならない規則と取り決めを置く

- 日付：2026-11-22
- 状態：採用

## 状況

[ADR 14](0014-folder-layout.md) は、`core/` に置くものを「2 か所以上から使う規則と、その間の取り決め」と決めた。実際の `core/` には、CLI だけが使う手順（鍵の保存と削除、同期の計画と S3 への書き込み、コマンドの引数の解釈）と、Lambda だけが使う読み込み（SSM の鍵）が入っていた。

使う所の数は、規則が変わらなくても増減する。数で決めると、規則でない手順が 2 か所目に使われた時点で `core/` に入り、1 か所でしか使わない規則は外に出ることになる。

## 決定

- `core/` には、どの実行環境（CLI・Lambda・ブラウザ・CDK）でも同じでなければならない規則と、環境の間の取り決めを置く。使う所の数では決めない
- 迷ったら、「これを変えたら、使っているすべての環境に同じ変更が要るか」で決める
- I/O を持つかどうかでは分けない。S3 のページの一覧（`listRemote`）と手元の鍵・状態の場所（`paths`）は、CLI と Lambda、CLI と CDK の間の取り決めとして `core/` に置く
- この基準で、次を移す
  - 期限のコマンドの引数の解釈（`parseLifetimeMs`）、同期の計画と歯止め（`planSync`・`assertSafeToApply`）、S3 への書き込み（`applyPlan`）、鍵の保存・削除・デプロイ済みの世代の読み出し → `cli/lib/`
  - SSM の鍵の読み込み（`loadSigningKey`）→ `functions/`
- 署名付き URL の形（`signPageUrl`）は、Lambda だけが使うが、URL の規則なので `core/` に残す

ADR 14 の「ディレクトリ」の表の `core/` の行と、`core/` についての理由は、この ADR で置き換える。依存の向き・型検査・テストとソースの対応は ADR 14 のまま。

## 理由

- `core/` を変えたら、すべての環境に同じ変更が要る（Lambda は deploy するまで古い規則のまま）。この区別が置き場所から分かるようにするため
- 規則かどうかは、使う所が増えても変わらない。置き場所を動かさずに済む

## 捨てた案

- 使う所の数で決める（ADR 14）：上の「状況」のとおり、置き場所が規則の性質と関係なく動く
- `core/` を、AWS や手元のファイルに触れない純粋な関数だけにする：境界ははっきりするが、CLI と Lambda が同じ一覧のしかたを使う `listRemote` を置く場所が別に要る。取り決めは 1 か所に置いたほうが食い違わない

## 結果

- S3 の送信の型（`S3Sender`）は `listRemote` と一緒に `core/` に置く。SSM の送信の型（`SsmSender`）は、使う `cli/lib/` と `functions/` にそれぞれ置く。どちらも `send` だけを持つ同じ形で、テストは `test/helpers/fake-sender.ts` の偽物を共有する
- Lambda のバンドルの中身は変わらない（CLI だけが使う関数は、移す前から esbuild が落としていた）
