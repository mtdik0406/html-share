# develop

コードを変える作業を、始めから報告まで毎回同じ順で進める。ユーザーは、できあがったものを確認するだけにしたい。そのため、振る舞いの決定から実装・レビュー・修正までをこちらで済ませ、ユーザーには結果と、ユーザーにしか決められないことだけを渡す。

```
作る：1 準備 → 2 振る舞いを決める → 3 TDD
見る：4 検査 → 5 レビュー → 6 確かめる → 7 直す → 8 もう一度見る
渡す：9 報告
```

「レビューして」のようにレビューだけを頼まれたときは、4 から始め、7 と 8 を飛ばして 9 で止める。頼まれていない修正とコミットは、ユーザーの予想に反するため。

機械で決められることは、AI が出力を読んで判断せず、コマンドの終了コードと出力に従う。判断がセッションごとに分かれないようにするため。AI の判断は、意味の読み取りにだけ使う。

| 決めること                                                                     | 従うもの                                                                                                        |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| テストが、まだ実装していないから落ちているか                                   | `pnpm run tdd:red <テストのファイル>`（終了コード 0 なら落ちている）                                            |
| 型・書式・lint・複雑さ・リポジトリの約束・未使用のコード・重複・テストと網羅率 | `pnpm run check`（コミットのときに pre-commit も実行する）                                                      |
| テストが見逃す所の候補                                                         | `pnpm run test:mutation:scope` のあとの `pnpm run review:mutants [ファイル]`（一覧を出す。直すかは 7 で決める） |
| 範囲・ユーザーの判断が要る変更・レビューのエージェントの数                     | `pnpm run review:scope`                                                                                         |

## 1. 準備

- main にいたら、`<種類>/<内容>` の名前で作業ブランチを作る（種類は `feat`・`fix`・`refactor`・`chore`）。main は公開リポジトリに push するので、確認される前の変更を混ぜないため
- 変える所に関係する `docs/adr/` を読む。ADR で決めた方針を変える必要があると分かったら、実装の前にユーザーに相談する。方針に反するコードを書いてから気づくと、書いた分が無駄になるため
- 変える所が検査や規則のファイル（`review:scope` が「ユーザーの判断が要る変更」に挙げるもの）に及ぶなら、変える内容を先にまとめ、報告で 1 回だけ尋ねる

## 2. 振る舞いを決める

変えたあとの振る舞いを、外から見える形で箇条書きにする（入力・出力・失敗するときの条件）。この箇条書きがテストの一覧になり、レビューの基準と、報告の「決めた振る舞い」にもなる。

- 依頼があいまいなら、立てた仮定を先頭に書いて進める。ユーザーにしか決められないこと（仕様の選択・費用・公開の範囲）だけを尋ねる
- 境界値は、通る側と止まる側の両方を挙げる
- 失敗の経路（入力の誤り・外部の失敗・途中で止まったとき）も挙げる

## 3. TDD

箇条書きの 1 項目ずつ、次を繰り返す。7 で指摘を直すときも同じ手順を使う。

1. **テストを書く**：振る舞いを外から確かめるテストを書く。新しい関数なら、先に型だけ合う仮の実装を置く。仮の実装は例外を投げず、型の合う既定の値（空の配列・`false` など）を返す。例外を投げる仮の実装だと、「失敗すること」を確かめるテストが実装の前から通ってしまうため
2. **落ちることを確かめる**：`pnpm run tdd:red test/<パス>.test.ts`（`<パス>.ts` のテストは `test/<パス>.test.ts` に置く）。終了コードが 0 でなければ、出力に従ってテストか仮の実装を直し、もう一度実行する
3. **実装する**：テストを通すのに要る分だけ書く
4. **通ることを確かめる**：`pnpm exec tsx --test test/<パス>.test.ts`
5. **整える**：テストが通ったまま、重複や名前を直す
6. **コミットする**：その項目のテストと実装を 1 つのコミットにする。pre-commit の `pnpm run check` が落ちたら直す。検査を弱めない

2 と 4 の出力の要点（落ちたテストの名前と、通った件数）は、報告に載せるので控えておく。

作業の種類で、始め方が変わる。

- **バグの修正**：直す前に、バグを再現するテストを書き、`tdd:red` で落ちることを見る。再現できないバグは、直したと言えない
- **振る舞いを変えないリファクタリング**：新しいテストは書かない。変える前と後で、テストの件数と結果、生成物（`pnpm exec cdk synth` のテンプレートなど、変える所が作るもの）が同じことを確かめる。以前からある見逃した変異を、先に片づけない（ADR 18）
- **機械的な書き換え**（スクリプトでの一括置換など）：書き換えたあと、狙った行（import など）以外の差分がないことを `git diff` で確かめる。テストの入力の文字列まで書き換わることがあるため

## 4. 検査

1. 範囲を決める。引数でファイルや範囲が指定されたらそれに従い、なければ `pnpm run review:scope` の「範囲」を使う。別のブランチに重ねたブランチでは、`review:scope`・`test:mutation:scope`・`review:mutants` に `--base <親のブランチ>` を渡す。先に main を最新にする（手元の main が古いと、ほかの変更まで範囲に入る）。「ユーザーの判断が要る変更」は、そのまま報告に写す
2. `pnpm run check`。落ちたら、レビューの前に直す
3. `pnpm run test:mutation:scope`。TDD のコミットごとには流さず、この検査の段階で流す（流し直すのは 8 の場合だけ）。変えたファイルだけを、前回の結果を使って流す。どのソースに効くか分からない変更（helper・依存・設定）があれば、スクリプトが全体を流して前回の結果を作り直す。結果が怪しいときは `--all` で作り直す。一部のファイルだけを流すと、スコアの下限で落ちることがあるが、止まらずに 4 へ進む。下限で止めるのは CI の全体の実行だけ（ADR 18）。CI の全体の実行は main への push で流れ、取り込んだあとに気づく歯止めになる（ADR 19）
4. `pnpm run review:mutants`。見逃した変異の一覧を控える。終了コードが 0 でなくても、作業を止める理由にはしない（直すかは 7 で決める）

## 5. レビュー

エージェント（`general-purpose`）の数は、`review:scope` が出す数に従う。差分が小さいときに観点ごとに立てると、同じ文書とコードを何度も読ませるだけで、見つかるものはほとんど増えないため。

- 1 体：4 つの観点をすべて渡す
- 2 体：「正しさ＋テストの過不足」と「変更容易性＋セキュリティ」に分ける

2 体のときは、1 つのメッセージで同時に立てる。互いの結果に引きずられないようにするため。

各エージェントには、下の共通の指示と、受け持つ観点だけを渡す。こちらの見立てや直し方の案は渡さない。案を渡されたエージェントは、それを裏づける方向に読みやすく、独立したレビューにならないため。

### 共通の指示（そのまま渡す）

```
html-share リポジトリのレビュー。範囲：`git diff <基点>..HEAD`（未コミットの変更があれば含める）のうち <ファイル>
決めた振る舞い：<2 の箇条書き。なければ「なし」>
関係する ADR：<docs/adr/ の番号。なければ「なし」>
まず AGENTS.md と関係する ADR を読み、このリポジトリの規則と、決めた設計とその理由を知ってから、差分と対応するテストを読む。差分の外は、要るときだけ読む。
ファイルは編集しない。AWS を呼ぶコマンド、push、外部への送信はしない。確かめるための一時的なスクリプトやテストは、作業ディレクトリの外の一時ディレクトリに置く。一時ディレクトリで pnpm install をしない（リポジトリの node_modules のリンクが書き換わる）。テストは、リポジトリで `pnpm exec tsx --test <ファイル>` を流してよい。.keys/ の中は読まない。
観点：<観点>
指摘ごとに次を返す。指摘がなければ「なし」と返す。
- 重さ：高（壊れる・漏れる）／中（次の変更で壊しやすい）／低（好み・軽微）
- 場所：ファイル:行
- 起きる条件：どんな入力や状態で、何が起きるか
- 確かめ方：実行して確かめたか、読んだだけか
- 直し方：どう直すか、その代わりに何が増えるか
- ADR との関係：ADR で決めた方針を変える直し方なら、その ADR の番号
```

### 観点

書式・複雑さ・字面の重複・未使用のコード・エラーの文言を見るテスト・網羅率・変異は、4 の検査が見るのでエージェントに探させない。

- **正しさ**：決めた振る舞いと実装の食い違い、論理の誤り、境界での誤り（off-by-one・空・最大）、例外や途中の失敗のあとの状態
- **テストの過不足**：決めた振る舞いのうち、テストで確かめていないもの（境界値の両側・失敗の経路・処理の順序・外部の失敗）。逆に、内部の実装に依存していて、振る舞いを変えないリファクタリングで落ちるテスト
- **変更容易性**：同じ規則が形を変えて 2 か所以上にある所、入口のスクリプトに残った判断、テストで差し替えられない外部とのやり取り（S3・時刻・ファイルの場所）、1 つの変更で複数のファイルを直す必要がある形
- **セキュリティ**：手元の意図しないファイルや秘密値の公開、パスの解決（symlink・`..`・ハードリンク・ドットで始まるディレクトリ）、S3 の消しすぎと部分的な失敗、署名付き URL の期限、CSP と応答ヘッダー、依存とその取り込み方、hook や CI が実行するコード

## 6. 指摘を確かめる

エージェントは、起きない問題も自信のある書き方で返してくる。直す前に、指摘ごとに本当に起きるかを確かめる。

- 正しさ・テストの過不足：その条件のテストを書き、`tdd:red` の終了コードが 0 なら起きている
- 変更容易性：重複や依存を、コードの場所で示せるかを見る。示せないものは外す
- セキュリティ：一時ディレクトリで再現する。AWS が要るものは再現せず、「未確認」として報告に回す

起きないと分かった指摘は外す。2 つのエージェントが同じ所を指したら、1 つにまとめる。

今のコードにない書き方や入力でだけ起きる指摘（「この書き方もすり抜ける」など）は、起きると確かめられても直さず、報告の「直していないこと」に載せる。直すたびに範囲が広がり、作業が収束しなくなるため（ADR 18）。

## 7. 直す

確かめた指摘を、次のように振り分ける。迷ったらユーザーに回す。ユーザーの意図と違う方向に直すほうが、尋ねるより確認の手間が大きいため。

**こちらで直す**：高と中の指摘、下の基準に当たる変異、および低のうち振る舞いを変えずに小さく直せるもの。ただし下のどれにも当たらないものに限る。3 の手順で、指摘ごとに 1 つのコミットにする。

`review:mutants` が挙げた変異は、その変異で結果が変わる入力と、外から見える違いを挙げられるものだけを直す。挙げた入力でテストを書き、その変異を手で入れると落ち、戻すと通ることを確かめる。挙げられない変異（どう変えても結果が同じになるもの、表示の文言）は、テストも `// Stryker disable` のコメントも足さず、報告に数だけ載せる。コメントの正しさを確かめる手間と、変異を避けるためにコードの形を変える圧力を生むため（ADR 18）。変異のスコアの下限は、main への push の CI が守る。

**ユーザーに回す**（直さずに報告の「判断してほしいこと」に載せる）：

- ユーザーが決めた仕様や、ADR で決めた方針を変える直し方
- 範囲の外のモジュールに手を入れる直し方
- `review:scope` が「ユーザーの判断が要る変更」に挙げるファイルを変える直し方
- 直し方が複数あり、使い勝手や費用が変わるもの
- 確認が要る操作（push・AWS への操作・元に戻せない削除）が要るもの

## 8. もう一度見る

4 の 2 を実行し直す。変異のためにテストを足したときだけ、3 と 4 も流し直す。

高か中の指摘を直したときだけ、エージェントを 1 体立てる。範囲は直した差分だけにし、直した指摘があった観点だけを、同じ共通の指示で渡す。低の指摘と変異だけを直したときは立てない。直し方がテストで確かめられていて、もう一度読ませても見つかるものが少ないため。新しく確かめられた指摘があれば、7 に戻る。

もう一度見るのは 1 回までにする。それでも残った指摘は直さずに報告に載せる。直すたびに新しい指摘が出るなら、直し方の前提が違っている見込みが高く、ユーザーと話すべきため。

## 9. 報告

ユーザーが確認だけで済むように、次の形で書く。結論を先に書く。push と main への取り込みは、ユーザーの確認を待つ。

```
結論：<何ができたか 1 行>。レビューで N 件を直し、M 件はあなたの判断待ち。

確認のしかた
- <ユーザーが自分の目で確かめる手順。コマンドや見る画面>

決めた振る舞い
- <2 の箇条書き>

TDD
- <項目>：落ちる（<落ちたテストの名前>）→ 通る

レビューで直したこと
1. [高] <場所> <一言>：<起きる条件> → <どう直したか>（落ちる → 通る を確かめた）

ユーザーの判断が要る変更（review:scope の出力をそのまま）
- <ファイル>

直していないこと
- 外した指摘：N 件（<理由>）
- 直さなかった変異：N 件（結果が変わる入力を挙げられなかったもの）
- 未確認：<AWS が要るなどで確かめられなかったもの>

検査：pnpm run check（テスト N 件すべて成功）、変異テストのスコア N%、review:mutants の見逃し N 件（うち直した N 件）

判断してほしいこと
1. <ユーザーに回した指摘と、選択肢と、勧める案>
2. push して main に取り込んでよいか
```
