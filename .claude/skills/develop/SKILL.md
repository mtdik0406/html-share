# develop

コードを変える作業を、毎回同じ順で進める。ユーザーは、できあがったものを確認するだけにしたい。そのため、振る舞いの決定から実装までをこちらで済ませ、レビューと報告は quality-review に渡す。

```
1 準備 → 2 振る舞いを決める → 3 TDD（項目ごとに：テスト → 落ちる → 実装 → 通る → 整える → コミット）→ 4 quality-review
```

テストが正しい理由で落ちたか、テストが足りているかは、AI が出力を読んで判断せず、コマンドの終了コードに従う。判断がセッションごとに分かれないようにするため。

| 決めること                                   | 従うもの                                                             |
| -------------------------------------------- | -------------------------------------------------------------------- |
| テストが、まだ実装していないから落ちているか | `pnpm run tdd:red <テストのファイル>`（終了コード 0 なら落ちている） |
| 変える前の所を、今のテストが守っているか     | `pnpm run review:mutants <ファイル>`（終了コード 0 なら守っている）  |
| 型・lint・リポジトリの約束・テスト           | コミットのときに pre-commit が実行する `pnpm run check`              |

## 1. 準備

- main にいたら、`<種類>/<内容>` の名前で作業ブランチを作る（種類は `feat`・`fix`・`refactor`・`chore`）。main は公開リポジトリに push するので、確認される前の変更を混ぜないため
- `AGENTS.md` と、変える所に関係する `docs/adr/` を読む。ADR で決めた方針を変える必要があると分かったら、実装の前にユーザーに相談する。方針に反するコードを書いてから気づくと、書いた分が無駄になるため

## 2. 振る舞いを決める

変えたあとの振る舞いを、外から見える形で箇条書きにする（入力・出力・失敗するときの条件）。この箇条書きがテストの一覧になり、報告の「決めた振る舞い」にもなる。

- 依頼があいまいなら、立てた仮定を先頭に書いて進める。ユーザーにしか決められないこと（仕様の選択・費用・公開の範囲）だけを尋ねる
- 境界値は、通る側と止まる側の両方を挙げる
- 失敗の経路（入力の誤り・外部の失敗・途中で止まったとき）も挙げる

## 3. TDD

箇条書きの 1 項目ずつ、次を繰り返す。

1. **テストを書く**：振る舞いを外から確かめるテストを書く。新しい関数なら、先に型だけ合う仮の実装を置く。仮の実装は例外を投げず、型の合う既定の値（空の配列・`false` など）を返す。例外を投げる仮の実装だと、「失敗すること」を確かめるテストが実装の前から通ってしまうため
2. **落ちることを確かめる**：`pnpm run tdd:red test/<file>.test.ts`。終了コードが 0 でなければ、出力に従ってテストか仮の実装を直し、もう一度実行する
3. **実装する**：テストを通すのに要る分だけ書く
4. **通ることを確かめる**：`pnpm exec tsx --test test/<file>.test.ts`
5. **整える**：テストが通ったまま、重複や名前を直す
6. **コミットする**：その項目のテストと実装を 1 つのコミットにする。pre-commit が `pnpm run check` を実行し、落ちたらコミットできない。落ちたら直す。検査を弱めない（`AGENTS.md`）

2 と 4 の出力の要点（落ちたテストの名前と、通った件数）は、報告に載せるので控えておく。

作業の種類で、始め方が変わる。

- **バグの修正**：直す前に、バグを再現するテストを書き、`tdd:red` で落ちることを見る。再現できないバグは、直したと言えない
- **振る舞いを変えないリファクタリング**：新しいテストは書かない。先に `pnpm run test:mutation` を実行し、`pnpm run review:mutants <変えるファイル>` の終了コードが 0 になるまでテストを足す。テストが守っていない所を変えると、壊しても気づけないため

変える所が検査や規則のファイル（`pnpm run review:scope` が「ユーザーの判断が要る変更」に挙げるもの）に及ぶときは、変える内容を先にまとめ、報告で 1 回だけ尋ねる。

## 4. quality-review に渡す

箇条書きをすべてコミットしたら、`quality-review` の skill を最後まで実行する。報告はそちらが書く。2 の箇条書きと、3 で控えた結果を渡す。
