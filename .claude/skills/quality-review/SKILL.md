# quality-review

ユーザーは、できあがったものを確認するだけにしたい。そのため、レビュー・確かめ・修正まではこちらで済ませ、ユーザーには結果と、ユーザーにしか決められないことだけを渡す。最後の報告はこの skill が書く。

ユーザーが「レビューして」のようにレビューだけを頼んだときは、4 と 5 を飛ばし、確かめた指摘を報告して止める。頼まれていない修正とコミットは、ユーザーの予想に反するため。

機械で決められることは、判断せずにコマンドの終了コードと出力に従う。AI の判断は、意味の読み取りにだけ使う。

| 決めること                                                                     | 従うもの                                                                                   |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 範囲と、ユーザーの判断が要る変更                                               | `pnpm run review:scope`                                                                    |
| 型・書式・lint・複雑さ・リポジトリの約束・未使用のコード・重複・テストと網羅率 | `pnpm run check`                                                                           |
| テストが見逃す所                                                               | `pnpm run test:mutation` のあとの `pnpm run review:mutants`（終了コード 0 なら見逃しなし） |

## 1. 範囲と検査

main にいたら止まり、develop の 1 に従って作業ブランチを作る。

1. 引数でファイルや範囲が指定されたらそれに従い、なければ `pnpm run review:scope` の「範囲」を使う。「ユーザーの判断が要る変更」は、そのまま報告に写す
2. `pnpm run check` を実行する。落ちたら、レビューの前に直す
3. `pnpm run test:mutation` を実行する。スコアが下限を下回って落ちたら、下限を下げずにテストを足す
4. `pnpm run review:mutants` を実行し、見逃した変異の一覧を控える

## 2. 4 つのエージェントに渡す

4 つを 1 つのメッセージで同時に Agent（`general-purpose`）に渡す。並べて走らせるのは、互いの結果に引きずられないようにするためでもある。

各エージェントには、下の共通の指示と観点の 1 つだけを渡す。こちらの見立てや直し方の案は渡さない。案を渡されたエージェントは、それを裏づける方向に読みやすく、独立したレビューにならないため。

### 共通の指示（そのまま渡す）

```
html-share リポジトリのレビュー。範囲：<範囲>
決めた振る舞い：<develop の 2 の箇条書き。なければ「なし」>
まず AGENTS.md・README・docs/adr/ を読み、このリポジトリの規則と、決めた設計とその理由を知ってから、範囲のコードと対応するテストを読む。
ファイルは編集しない。AWS を呼ぶコマンド、push、外部への送信はしない。確かめるための一時的なスクリプトやテストは、作業ディレクトリの外の一時ディレクトリに置く。
観点：<観点>
指摘ごとに次を返す。指摘がなければ「なし」と返す。
- 重さ：高（壊れる・漏れる）／中（次の変更で壊しやすい）／低（好み・軽微）
- 場所：ファイル:行
- 起きる条件：どんな入力や状態で、何が起きるか
- 確かめ方：実行して確かめたか、読んだだけか
- 直し方：どう直すか、その代わりに何が増えるか
- ADR との関係：ADR で決めた方針を変える直し方なら、その ADR の番号
```

### 観点

書式・複雑さ・字面の重複・未使用のコード・エラーの文言を見るテスト・網羅率・変異は、検査が見るのでエージェントに探させない。

- **正しさ**：決めた振る舞いと実装の食い違い、論理の誤り、境界での誤り（off-by-one・空・最大）、例外や途中の失敗のあとの状態
- **テストの過不足**：決めた振る舞いのうち、テストで確かめていないもの（境界値の両側・失敗の経路・処理の順序・外部の失敗）。逆に、内部の実装に依存していて、振る舞いを変えないリファクタリングで落ちるテスト
- **変更容易性**：同じ規則が形を変えて 2 か所以上にある所、入口のスクリプトに残った判断、テストで差し替えられない外部とのやり取り（S3・時刻・ファイルの場所）、1 つの変更で複数のファイルを直す必要がある形
- **セキュリティ**：手元の意図しないファイルや秘密値の公開、パスの解決（symlink・`..`・ハードリンク・ドットで始まるディレクトリ）、S3 の消しすぎと部分的な失敗、署名付き URL の期限、CSP と応答ヘッダー、依存とその取り込み方、hook や CI が実行するコード

## 3. 指摘を確かめる

エージェントは、起きない問題も自信のある書き方で返してくる。直す前に、指摘ごとに本当に起きるかを確かめる。

- 正しさ・テストの過不足：その条件のテストを書き、`pnpm run tdd:red` で落ちる（終了コード 0）なら起きている
- 変更容易性：重複や依存を、コードの場所で示せるかを見る。示せないものは外す
- セキュリティ：一時ディレクトリで再現する。AWS が要るものは再現せず、「未確認」として報告に回す

起きないと分かった指摘は外す。2 つのエージェントが同じ所を指したら、1 つにまとめる。

## 4. 直す

確かめた指摘を、次のように振り分ける。迷ったらユーザーに回す。ユーザーの意図と違う方向に直すほうが、尋ねるより確認の手間が大きいため。

**こちらで直す**：高と中の指摘、`review:mutants` が挙げた変異、および低のうち振る舞いを変えずに小さく直せるもの。ただし下のどれにも当たらないものに限る。

変異のうち、表示の文言や、どう変えても振る舞いが同じになる変異は、テストを足さずに `// Stryker disable next-line <変異の名前>: <理由>` をその行の上に書いて外す。理由がコードに残り、次のセッションでも同じ扱いになるため。

**ユーザーに回す**（直さずに報告の「判断してほしいこと」に載せる）：

- ユーザーが決めた仕様や、ADR で決めた方針を変える直し方
- 範囲の外のモジュールに手を入れる直し方
- `review:scope` が「ユーザーの判断が要る変更」に挙げるファイルを変える直し方
- 直し方が複数あり、使い勝手や費用が変わるもの
- 確認が要る操作（push・AWS への操作・元に戻せない削除）が要るもの

直すときは develop の 3 に従う（指摘を再現するテスト → `tdd:red` → 実装 → 通る → コミット）。指摘ごとに 1 つのコミットにする。push と main への取り込みは、ユーザーの確認を待つ。

## 5. 直した所をもう一度見る

`pnpm run test:mutation` と `pnpm run review:mutants` を実行し直す。直した差分だけを範囲にして、直した指摘があった観点のエージェントだけを、同じ共通の指示で立て直す。新しく確かめられた指摘があれば、4 に戻る。

もう一度見るのは 1 回までにする。それでも残った指摘は直さずに報告に載せる。直すたびに新しい指摘が出るなら、直し方の前提が違っている見込みが高く、ユーザーと話すべきため。

## 6. 報告する

ユーザーが確認だけで済むように、次の形で書く。結論を先に書く。

```
結論：<何ができたか 1 行>。レビューで N 件を直し、M 件はあなたの判断待ち。

確認のしかた
- <ユーザーが自分の目で確かめる手順。コマンドや見る画面>

決めた振る舞い
- <develop の 2 の箇条書き>

TDD
- <項目>：落ちる（<落ちたテストの名前>）→ 通る

レビューで直したこと
1. [高] <場所> <一言>：<起きる条件> → <どう直したか>（落ちる → 通る を確かめた）

ユーザーの判断が要る変更（review:scope の出力をそのまま）
- <ファイル>

直していないこと
- 外した指摘：N 件（<理由>）
- Stryker disable で外した変異：N 件（<理由>）
- 未確認：<AWS が要るなどで確かめられなかったもの>

検査：pnpm run check（テスト N 件すべて成功）、変異テストのスコア N%、review:mutants の見逃し 0 件

判断してほしいこと
1. <ユーザーに回した指摘と、選択肢と、勧める案>
2. push して main に取り込んでよいか
```
